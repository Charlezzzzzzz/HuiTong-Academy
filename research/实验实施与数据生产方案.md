> **日期**：2026-10-31（Asia/Shanghai）
>

> **定位**：本文档把会通系统中的“运行、记录、导出、脱敏、评分、分析和论文报告”串成一条可复现数据链。它描述的是研究实施方案，不把计划运行、fixture 输出或草评分写成已经得到的实证结论。

## 1. 先区分三个问题

会通需要同时支持三类数据用途，但三类数据不能混用：

| 数据用途 | 主要问题 | 允许的结论 |
|---|---|---|
| 编辑阶段压力测试 | 受约束编辑是否更能保持必要限定、有效异议和原有论证强度 | 系统机制对模型输出的影响 |
| 人机协作过程记录 | 学习者如何选择席位、调用证据、提出问难和修改主张 | 系统行为、过程可追溯性和交互模式 |
| 学习成效研究 | 学习者是否真正学会并能迁移 | 需要独立前测、对照、变式题和延迟测验；当前项目暂不声称这一点 |

第一轮正式研究只把第一类作为 GCCCE 机制实验；第二类服务课程毕设和学习分析；第三类保留为后续教学实验。

## 2. 当前工程已经具备的实验基础

当前 `research/` 已有：

- `cases.jsonl`：12 个冻结案例，`error`、`plural`、`insufficient` 各 4 个；
- `conditions.json`：普通编辑和受约束编辑；
- `runs/manifest.jsonl`：12 个案例 × 2 个条件 × 3 次重复，共 72 条唯一运行计划；
- `run_fixture.py`：只读取 manifest 中的生成输入快照，产生带 `run_type=fixture` 的确定性数据；
- `run_live.py`：只读取 manifest 中的生成输入快照，执行一次最终编辑调用并记录可审计的 live/failed 元数据；
- `score_outputs.py`：开发阶段草评分和案例层聚合；
- `validate_runs.py`：检查运行唯一性、完整性、哈希、运行类型分离和金标准字段泄漏；
- `annotation_only.jsonl`：评分端金标准，生成端禁止读取；
- `runs/run_records.jsonl`、`runs/validation.json`、`runs/summary.json`：当前 fixture 管线的运行审计产物。

当前 fixture 运行已经可以验证数据路径，但它不是模型实验。现有 72 条完成记录的 `run_type` 是 `fixture`，因此不能在论文中写成 DeepSeek 模型结果，也不能写成学生学习结果。

## 3. 第一轮正式机制实验

### 3.1 研究问题

当两个条件获得完全相同的中间论证材料、证据核验结果和争议状态时，显式的“论证保持 + 必要限定保留 + 异议承载 + 语义变更记录”规则，是否能减少最终文章中的无依据确定化，并提高有效替代解释与必要限定的保留？

### 3.2 实验条件

两个条件只在最终编辑规则上不同：

**普通编辑**：

> 根据相同的中间论证材料写成一篇可读文章，忠实呈现材料。

**受约束编辑**：

> 写成可读文章；保持原有论证强度，保留必要限定和有证据支持的替代解释，记录语义变更及其理由，不把未决问题改写成确定结论。

每个运行只进行一次最终编辑调用。12 个案例 × 2 个条件 × 3 次重复 = 72 条运行计划。重复运行是模型稳定性观察，不是 72 个独立研究情境；主要分析单位是案例。

### 3.3 案例结构

每个案例至少包含：

```json
{
  "case_id": "plural_01",
  "case_type": "plural",
  "title": "会通中的主持权",
  "task": "...",
  "source_ids": ["P04", "P05", "P08"],
  "required_elements": ["..."],
  "required_qualifiers": ["..."],
  "supported_alternatives": ["..."],
  "incorrect_views": []
}
```

`required_elements`、`required_qualifiers`、`supported_alternatives` 和 `incorrect_views` 只属于评分端金标准。它们不得出现在模型提示、生成输出或运行记录中。

## 4. 一次实验运行到底要产生什么数据

### 4.1 运行身份数据

每条运行必须有唯一 `run_id`，并记录：

- `case_id`、`case_type`、`condition_id`、`replicate`；
- `protocol_version`、`prompt_version`、`config_hash`、`input_hash`；
- `model`、provider、reasoning effort、运行类型；
- `status`：`planned`、`running`、`completed`、`failed`、`fallback`；
- `attempt`、`retry_count`、开始时间、结束时间、延迟；
- 输入 token、输出 token、错误类别和错误摘要；
- 输出哈希。

建议的最小记录如下：

```json
{
  "run_id": "...",
  "case_id": "error_01",
  "condition_id": "constrained_edit",
  "replicate": 1,
  "run_type": "live",
  "status": "completed",
  "model": "deepseek-v4.1-flash-1017",
  "prompt_version": "editor-v1.0.0",
  "protocol_version": "huitong-edit-pressure-v1",
  "input_hash": "sha256...",
  "output_hash": "sha256...",
  "attempt": 1,
  "retry_count": 0,
  "latency_ms": 0,
  "input_tokens": 0,
  "output_tokens": 0,
  "error": null
}
```

### 4.2 模型输出数据

模型输出分成两层保存：

1. `outputs_raw.jsonl`：保留模型可见的输入摘要、结构化输出、调用元数据和原始文本；
2. `outputs_structured.jsonl`：只保留经过本地校验后的结构化字段，供评分程序使用。

推荐输出结构：

```json
{
  "run_id": "...",
  "case_id": "error_01",
  "condition_id": "constrained_edit",
  "run_type": "live",
  "status": "completed",
  "text": "...",
  "structured": {
    "stage": "constrained_edit",
    "main_claims": [
      {"claim_id": "C-001", "text": "...", "evidence_ids": ["E-002"], "confidence": "qualified"}
    ],
    "qualifiers": ["..."],
    "dissent": [
      {"text": "...", "status": "preserved", "evidence_ids": ["E-004"]}
    ],
    "edit_audit": [
      {"change": "added_qualifier", "reason": "证据只支持限定结论"}
    ]
  },
  "validation_status": "accepted"
}
```

模型隐藏思维过程不保存、不展示、不作为评分对象。只保存对用户和研究者可解释的结果字段。

## 5. 运行流程

### 5.1 运行前冻结

在第一次 live 运行前，冻结以下内容并计算哈希：

1. `cases.jsonl` 和材料包版本；
2. `conditions.json`；
3. 提示模板和结构化输出协议；
4. 模型名、区域、推理强度和网关版本；
5. 评分字段、人工编码手册和 `annotation_only.jsonl`；
6. manifest 生成时间和 Git/文件快照。

如果提示、材料或评分规则发生改变，应提高 `prompt_version` 或 `protocol_version`，不要覆盖旧运行。

### 5.2 先跑 fixture

```bash
cd "/Users/charleslu/Documents/人工智能前沿/人工智能前沿工作区/huitong-web"
python3 research/generate_manifest.py
python3 research/run_fixture.py
python3 research/validate_runs.py
python3 research/score_outputs.py --outputs research/outputs.jsonl
```

fixture 的验收目标是：72 个 `run_id` 唯一、输出完整、哈希一致、没有金标准字段泄漏、评分表可以生成。

### 5.3 再做 live

live 运行必须：

- 使用同一份冻结 manifest；
- 不读取 `annotation_only.jsonl`；
- 不启用外部搜索；
- 每个运行只调用一次最终编辑模型，重试只用于网络/格式失败；
- 重试次数、失败原因和最终状态全部记录；
- fixture、mock、fallback 和 live 输出分目录或至少用 `run_type` 严格区分。

当前工程已经有网关、fixture 管线和独立的 `run_live.py`。正式 live runner 仍应在运行前冻结材料、提示和协议并单独审计。没有真实 Key 时，只能运行 fixture 或 mock，不能伪造 live 结果。

## 6. 评分设计

### 6.1 主指标

每篇文章先进行主张级编码，再汇总到案例层。主指标包括：

1. **必要主张元素覆盖率**：金标准要求的主张元素中，被正确表达的比例；
2. **必要限定保留率**：必要限定是否保留，且没有被改写成更强结论；
3. **有效替代解释保留率**：有材料支持的替代解释是否被保留并放在合适位置；
4. **错误观点保留率**：明确错误观点被最终文章保留的比例，越低越好；
5. **无依据确定化率**：原本限定或未决的内容被改写成确定断言的比例；
6. **编辑记录忠实度**：`edit_audit` 是否准确反映文本中实际发生的语义变化。

### 6.2 次指标

- 证据—主张对齐率；
- 文章可读性和结构完整性；
- 文本长度、token 使用量和延迟；
- JSON 校验失败率、重试次数和最终失败率；
- 异议状态标注是否与最终文章承载位置一致。

关键词覆盖率只能用于开发阶段检查数据管线。正式论文应采用人工或专家语义编码，不能把关键词命中率直接解释成论证质量。

### 6.3 人工编码

建议至少两名编码者对全部输出或预先抽取的样本进行盲评：

- 编码者看不到条件标签和模型运行顺序；
- 每个指标使用 0/1 或 0–1 比例编码，并提供“无法判断”选项；
- 分歧先按编码手册复核，仍不能解决时由第三人仲裁；
- 记录 `annotation_version`、编码者编号、仲裁状态和修改时间；
- 报告 Cohen’s kappa、Krippendorff’s alpha 或百分比一致率，并说明指标类型和缺失处理。

人工评分文件应放在生成端无法读取的目录，至少与 `research/annotation_only.jsonl` 保持同等隔离级别。

## 7. 分析单位和统计方式

不要把 72 次模型调用直接当作 72 个独立样本。推荐流程：

1. 对每篇输出进行主张级编码；
2. 在同一 `case_id × condition_id` 内汇总 3 次重复，使用均值或中位数；
3. 对每个案例计算“受约束编辑 − 普通编辑”的差值；
4. 报告 12 个案例的均值、中位数、案例层差值和分层结果；
5. 使用配对 bootstrap 或配对符号置换区间；
6. 按 `error`、`plural`、`insufficient` 分层展示；
7. 同时报告失败、缺失和重试敏感性分析；
8. 不在看完结果后更改主指标，也不以单一 p 值作为唯一结论。

如果某一案例所有重复都失败，应保留该案例的失败状态，并在主分析和完整案例敏感性分析中分别说明。

## 8. 真实会话数据如何产生

### 8.1 事件来源

学习模式和生产模式中的关键行为由房间事件记录：

- 房间创建；
- 参与者入席；
- 当前阶段；
- 人类发言或选择；
- 主张、证据、问难、回应和修订；
- 异议登记与处理状态；
- 生成模型调用结果和错误；
- 会谈结束和导出时间。

当前前端“查看会录”会调用：

```text
GET /api/rooms/{room_id}/export
```

该接口返回房间摘要、参与者、事件、事件数量和模型安全摘要，不返回 API Key。当前版本已经接入房间级 participant token 与成员校验；正式多人部署前仍需补 token 撤销、并发推进保护、多进程共享限流和更完整的审计能力。

### 8.2 浏览器导出与脱敏

完成会通后点击“查看会录”，浏览器会下载类似：

```text
huitong-room-xxxxxxxx.json
```

使用研究脚本脱敏：

```bash
export HUITONG_RESEARCH_SALT='只保存在研究者本机的随机字符串'
python3 research/normalize_room_export.py \
  --input /path/to/huitong-room-xxxxxxxx.json \
  --events-output research/processed/session_events.jsonl \
  --summary-output research/processed/session_summary.json
```

脱敏脚本会：

- 对房间、参与者、发言者、事件和身份字段做带盐哈希；
- 保留席位、阶段、事件类型、可见性、文本和时间顺序；
- 生成事件 JSONL 和会话摘要 JSON；
- 不读取、不复制 `annotation_only.jsonl`；
- 记录事件数量、阶段分布、持续时间和模型运行类型。

原始导出文件含有用户发言，不能直接进入论文附件、公开仓库或聊天记录。研究者应先保存到受限目录，再完成脱敏和人工去识别。

### 8.3 过程数据字典

| 字段 | 来源 | 含义 | 是否用于当前 GCCCE 主结论 |
|---|---|---|---|
| `room_hash` | 脱敏导出 | 一场会通的匿名标识 | 否，作为分组键 |
| `event_hash` | 脱敏导出 | 单个事件的匿名标识 | 否，作为追溯键 |
| `type` | 房间事件 | 事件类型 | 否，过程描述 |
| `stage` | 房间事件 | 当前会通阶段 | 否，过程描述 |
| `actor_hash` | 脱敏导出 | 匿名参与者 | 否，过程描述 |
| `seat_id` | 事件 payload | 功能席位 | 否，过程描述 |
| `visibility` | 房间事件 | room/seat/private/research | 否，权限审计 |
| `payload.text` | 人类或代理事件 | 发言/修订文本 | 否，需人工编码 |
| `created_at` | 房间事件 | 事件时间戳 | 否，节奏和顺序 |
| `duration_seconds` | 摘要 | 会谈持续时间 | 否，描述性指标 |

## 9. 课程数据分析分支

如果课程要求展示“原始数据—表示—目标—评测”，可以单独建立学习者问题分类任务：

### 原始数据

匿名化的人类发言、任务上下文、阶段、席位、证据选择、异议处理和修订事件。

### 表示

- 中文文本；
- 阶段编码和席位编码；
- 证据图特征；
- 修订前后文本差异；
- 问题与主张/证据的绑定关系。

### 目标

将学习者问题标记为一个或多个类别：

- 概念解释；
- 步骤提示；
- 错误定位；
- 任务规则澄清。

### 评测

- 按学习者分组切分训练、验证和测试，避免同一学习者文本泄漏到不同集合；
- 报告每一类 Precision、Recall、F1；
- 同时报告 Macro-F1 和 Micro-F1；
- 通过教师盲评抽查分类合理性；
- 明确这项分类性能不是学习效果，也不是论证质量本身。

## 10. 失败、重试和数据质量规则

每次运行都要区分：

- 模型返回格式错误；
- 网络超时；
- 限流；
- 空输出；
- 本地结构校验失败；
- 运行中断；
- 人工评分缺失；
- 研究者主动放弃。

失败运行不删除、不静默补齐。允许重试，但必须增加 `attempt` 或 `retry_count`，并保留原始错误摘要。`fallback` 只能表示经过明确标记的替代运行，不能和 live 结果混在一起。

每次分析前运行：

```bash
python3 research/validate_runs.py
```

如果报告 `manifest_outputs_missing`、`output_run_id_not_unique`、`output_hash_mismatch` 或 `gold_field_names_in_generation_records`，应先修复数据链路，再进行评分和写作。

## 11. 课程毕设与 GCCCE 写作边界

### 课程毕设可以写

- 完整系统架构和交互流程；
- 登录、模型配置、会录导出和研究脚手架；
- fixture 数据管线和自动校验；
- 12 个案例的设计逻辑；
- 人工编码和数据脱敏方案；
- 真实运行前的风险、伦理和隐私边界。

### GCCCE 小论文只写

- 受约束编辑机制；
- 普通编辑与受约束编辑的可复现实验条件；
- 已真实完成的运行和人工评分；
- 案例层指标、失败案例和局限。

以下内容不能写成已经得到的结果：

- fixture 的 72 次输出等于 DeepSeek 实验；
- 过程事件指标等于学生学习成绩；
- 系统已经提高写作能力、迁移或长期保持；
- 模型生成的内容自动就是事实或文献结论。
